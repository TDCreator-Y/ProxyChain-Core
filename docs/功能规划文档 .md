# 🎯 全平台级联代理客户端 (Proxy Chain) 功能规划文档 (PRD)

## 1. 产品愿景与核心定位

- 产品代号：ProxyChain Core
- 核心目标：为高阶网络需求用户（如跨境电商、海外社媒运营）提供一套稳定、安全且易于管理的网络隔离方案。
- 核心机制：双重代理链路 (Dual-Node Relay)。
- 第一跳 (Entry Node)：常规 VPN/机场节点，负责突破物理网络封锁和优化跨国路由。
- 第二跳 (Exit Node)：纯净独享 ISP 节点，负责提供最终业务请求的真实且固定的 IP 伪装。
- 部署平台：第一阶段（桌面端 Windows/macOS），第二阶段（移动端 iOS/Android）。

## 2. 第一阶段 (MVP) 核心功能模块

这是产品从 0 到 1 必须跑通的最小功能集合。

### 2.1 仪表盘 (Dashboard)

负责展示当前系统的网络状态并提供高频操作入口。

- 主控开关：全局网络接管的启动/停止按钮。
- 状态面板：
  - 连接状态（未连接 / 连接中 / 已连接）。
  - 双节点状态显示：直观展示当前串联的 [VPN 节点名] -> [固定 ISP IP 地址及归属地]。
- 网络监视器：
  - 实时上行/下行速率（以 KB/s 或 MB/s 显示）。
  - 当前运行模式（TUN 虚拟网卡模式 / 系统代理模式）。

### 2.2 链路构建器 (Chain Builder)

区别于传统代理软件的核心交互界面，采用“双列选择”或“双层抽屉”设计。

- 入口组 (Entry Pool)：展示从订阅链接拉取的所有常规节点。支持按国家/地区分组、延迟排序。
- 出口组 (Exit Pool)：展示用户手动添加的或从特定订阅获取的 ISP 节点列表。
- 智能绑定：用户分别在入口组和出口组选中一个节点后，系统自动在底层将其配置为一个 Relay 策略组。

### 2.3 节点与订阅管理 (Nodes & Subscriptions)

- 订阅解析：
  - 支持标准的 Base64 / YAML 订阅链接。
  - 支持手动更新和应用启动时自动更新。
- 手动导入：支持通过剪贴板导入单节点链接（如 ss://, vmess://, trojan://）。
- 自定义固定节点：允许用户手动填写服务器 IP、端口、密码和加密方式，以添加自购的 ISP 服务器。

### 2.4 路由分流规则 (Routing Rules)

- 全局模式 (Global)：接管设备的所有流量，强制通过代理链。
- 规则模式 (Rule)：基于预设的 GeoIP / GeoSite 规则文件。
  - 中国大陆 IP / 常见国内域名 -> 直连 (Direct)。
  - 海外 IP / 域名 -> 代理链 (Proxy)。
- 模式切换：支持在 UI 上一键切换上述模式，底层动态重载路由规则而不中断连接。

### 2.5 基础设置 (Settings)

- TUN 引擎控制：开关虚拟网卡模式，选择是否开启 Strict Route（严格路由，防止流量绕过 TUN）。
- 开机自启动：跟随系统启动。
- 深色/浅色模式：UI 主题切换。

## 3. 第二阶段 (进阶) 功能规划

这部分功能可在核心逻辑跑通后逐步迭代。

- 全链路真实测速 (True-Link Ping)：传统软件只能测本地到 VPN 的延迟。本功能将测试 本地 -> VPN -> ISP -> Google/Cloudflare 的完整 TCP 握手延迟。
- DNS 泄漏绝对防护 (DNS Leak Protection)：
  - 强制开启 Fake-IP（伪装 IP）模式，接管系统所有的 DNS 请求。
  - 将真实的域名解析请求打包在加密隧道中，强制送到最后一跳（固定 ISP 节点）进行解析，彻底杜绝本地 DNS 污染和 IP 地域与 DNS 地域不符的风险。
- 应用级路由 (App-Based Routing - 仅限 Android/Windows)：基于应用包名或进程名（Process Name）决定哪些软件走代理链，哪些走直连。

## 4. 交互与数据流规范 (供 AI 开发参考)

为了让前端 Flutter 和底层 Rust 协同工作，核心数据流必须清晰：

- 节点数据模型 (Node Model)：
  - 前端统一使用 JSON/Dart Class 与 Rust 交互。
  - 包含字段：id (UUID), name, protocol (ss/trojan/socks5), server, port, uuid/password, tls_settings。
- 启停控制流：
  - 用户点击连接 -> Flutter 读取选中的 Entry Node 和 Exit Node 数据 -> 序列化后通过 FFI 传递给 Rust start_engine(entry, exit, config) -> Rust 启动 Tokio 运行时，建立 TUN 网卡，监听流量并映射到代理链 -> Rust 返回 true/false 给 Flutter。
- 状态监控流：
  - Rust 维持一个内部的计数器计算流量 -> 通过 FFI 的 Stream 机制每秒向 Flutter 发送一次 TrafficStatus { up: u64, down: u64 } -> Flutter 使用 Riverpod 监听 Stream 并刷新 UI。

## 5. 异常处理与降级策略

- 网络断开：当入口节点或出口节点之一失效时，Rust 底层必须抛出明确的断流事件给 UI。
- TUN 权限不足：在 Windows/macOS 上启动 TUN 需要管理员权限。如果获取失败，软件应提示用户提权，或自动降级为“系统代理 (System Proxy)”模式。
- 端口冲突：如果默认监听的混合端口（如 7890）被占用，Rust 核心应自动寻找可用端口并通知 UI 更新。
